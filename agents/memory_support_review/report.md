## 结论与适用版本

2026-09-26 通过远端查询确认，分支头为 `f06371ffb420becb6d325772aeeaf2336276bd16`。当前 Isla 工作树 HEAD 为 `f4f8e45`，共同祖先为 `0008fae76f4cff86dae1a036d889f0414c228e9d`；内存分支在共同祖先上有五个独立提交，不能把其能力直接归给当前工作树。

本轮是固定提交源码调查，没有构建该分支、运行新增 Rust/CLI 测试或重跑 `make solve`。下述行为由源码直接核对，举例用于说明逻辑，不冒充实测输出。底层多数限制来自继承的设计，并非本分支新引入；本分支没有消除这些限制。

## 支持思路：给每次访问记一张单

把一个内存地址想成一个编号抽屉。

读取未知内容时，底层新建一个待确定的数字，并记下“从这个抽屉取出这么多字节”。指令接下来可以使用这个数字继续运算、比较或决定执行方向。写入时，底层记下“准备往这个抽屉写这些字节”，再返回一个代表写入结果的未知真假值。

因此，单条指令先读出 A、再计算 A+1 并写回时，A 与 A+1 的关系仍由指令本身建立。缺失的是另一类关系：仅仅因为两次访问同一地址，或者覆盖了相同字节，就应当遵守同一份内存的前后内容规则。

源码：`memory.rs:619–670` 每次读取创建 fresh 值；`:679–704` 写入只创建返回值并追加事件。`Memory::new()` 在 `:245–246` 初始化 `client_info: None`；构造器没有装配回调。底层在 `:642–653,699–701` 留有补充这些规则的回调入口，但此分支的 `solve-state` 没有使用。[底层读写源码](https://github.com/ariscv/isla/blob/f06371ffb420becb6d325772aeeaf2336276bd16/isla-lib/src/memory.rs#L619)

## 已确认的关键缺口

### 1. 同址读取和写后读取没有自动关联

假设普通内存没有被其他执行者修改：

- 先读抽屉得到 A，再读同一抽屉得到 B，当前默认连接不会仅凭地址相同就要求 A=B。
- 写 7，再读同一抽屉，新读值不会自动被要求等于 7。
- 写四个字节，再从中间读一个字节，也没有自动建立对应字节的关系。

这既影响将来连续执行多条指令，也可能影响一条指令内重复或重叠访问同一位置的场景。当前 `solve-state` 本身按指令类别启动执行，不是一段长期运行、共享可变内存的程序。

已有 `Concrete` 区域是只读初始快照（`memory.rs:103–104`），不应当作可写 RAM。用户配置的 concrete 区域被构造为全零（`memory_builder.rs:191–204`）；具体地址写入除 Custom 外仍只记事件（`memory.rs:575–587`），没有改字节表。因此底层直接按这套连接访问时，读零、写 7、再读仍从初始表取得零。

### 2. 分区配置不自动等于访问范围限制

`memory_regions` 中声明某段内容未知，不意味着所有访问都被限定在该段。具体数据地址没有命中任何区域，仍可走默认未知读取（`memory.rs:526–530`）；未知地址排除具体区域重叠后也走 `default`（`:533–553`）。独立范围检查函数存在，但未见装配到此读写路径。

这不表示 RISC-V 指令模型不检查地址或权限；只是内存配置本身没有自动添加这项限制。若测试要求所有读写都在硬件某段 RAM 内，需要明确接上这个条件，并保留需要测试的越界/异常情形。

另一个限制是：地址仍有多种选择，且可能落进具体内容区域时，底层可能返回重叠错误，未自动拆开所有情况分别读取（`:390–427`）。默认构造器含具体内容的 CLINT 范围 `0x02000000..0x020c0000`；如果模型已经排除该范围或唯一确定地址，则不会因这个条件报错，不能说所有未知地址都会失败。

### 3. 访存 JSON 的顺序与执行顺序相反

`src/isarch/exec.rs:963–964` 直接遍历 `solver.trace().to_vec()`；`isla-lib/src/smt.rs:540–555` 先访问最新段，并对每段反向遍历。事件新增在末尾（`:2457–2459`），所以输出数组是后发生的访问在前。

例如，真实顺序为“读旧值 → 写新值”，JSON 中成为“写新值 → 读旧值”。只有一次访问的样例看不出差异；多个访问时，下游如果按数组顺序准备初始内存，会误解前后关系。

[输出收集位置](https://github.com/ariscv/isla/blob/f06371ffb420becb6d325772aeeaf2336276bd16/src/isarch/exec.rs#L961)、[底层倒序实现](https://github.com/ariscv/isla/blob/f06371ffb420becb6d325772aeeaf2336276bd16/isla-lib/src/smt.rs#L540)。

### 4. 输出是访存示例清单，还不是完整重放输入

每条记录的 `kind` 是读/写，`address` 是地址，`bytes` 是字节数；`value` 对读取表示读值，对写入表示写入结果，真正写的数据在 `data`。`region` 只是底层类型标签，常见为 `symbolic`、`concrete`、`default`，并不是配置中的 `sym_ram` 等名字；普通写和未知地址读通常使用 `default`，不能据此判断越界。

地址、输入寄存器和读写数据来自同一个求解结果查询，但只有已经建立的关系才会受到检查。没有同址一致性规则时，同一个求解结果也不能补出这条缺失的规则。

`exec.rs:787` 的完整具体取值选项仍注释掉。未知内容可能输出带有效位说明的字符串，并非一律 `null`；例如 `{8'h00, 8'b0000_0000}` 中零是占位，这些位没有被指定。写入结果的未知零占位同样不表示确定写失败。`fmtval.rs:117–122,186–190` 可确认这一点。下游需要区分确定数据、可自由选择的数据和取值失败。

JSON 未单独输出初始/最终内存，没有保留全部分支条件，且省略原始事件的详细访问种类、特殊读写选项和其他非读写事件（`exec.rs:966,976,990` 对照 `smt.rs:307–325`）。这不足以完整表达多次访问、特殊配对读写或处理器间访存关系。

当前根仓库 [XiangShan 程序生成入口](../../difftest-xiangshan/pipeline.py) 的 `make_assembly`（约 300 行）没有读取 `memory-events`；生成的数据用于向量寄存器初始化，case 信息也不保存该字段。所以“Isla 记录从 A 读到 7”尚未变成“硬件和参考模型在开跑前都把 A 填成 7，并在结束后检查该地址”。

### 5. 更复杂内存能力和运行规模仍需单独补齐

- 具体区域单次读取超过 8 字节会报错（`memory.rs:877–897`）。模型若拆成多次小读取则另论，不能推出所有向量读取都失败。
- 从具体区域末端跨到别的区域时，现读取实现按起始地址选择单个字节表，表中缺失字节按零处理；没有自动拼接后续区域（`:505–515,871–872`）。
- 已有页表构造预设被本次接线带入执行状态，但本分支没有新增真实地址转换全链路验收。具体页表的写入更新也不能靠上述只读快照自动完成。
- 预留一块设备地址的全零内容，并不因此具有计时器或设备读写副作用；完整模型的设备行为应单独核对。
- 向量访问涉及一次多个地址、重复地址、部分成功后异常等；特殊“读旧值并写新值”的指令还涉及额外访问关系。分支没有新增这些完整场景的通过证据。
- 分支没有针对真实 LOAD/STORE/AMO 的复杂地址和权限判断新增性能优化。测试中明确保留的耗时问题，不能视为接线后已消失。

## 测试到底证明了什么

新增三个执行器测试（`executor.rs:4522–4656`）分别检查内存被注入、传 None 保持默认、固定地址 `0x1000` 读取 1 字节并产生 symbolic 区域事件。最后一个确实到达底层读取，但没有覆盖未知地址、写入、多次访问的一致性或结果 JSON 的顺序。

新增 CLI 正向测试采用 `zC_LD`。测试源码 `test/isarch/cli/solve-state/test_isarch_cli_solve-state.sh:222–227` 明确说明，它只返回转换后的 `zLOAD`，没有真正读内存；因此测试只检查 JSON 字段和初始寄存器结构，没有断言实际读写事件。该处还说明真实 `zLOAD` 当时超过 15 分钟，不纳入此 CLI 用例。空的 `memory-events` 数组能满足相应字段检查。[测试原文](https://github.com/ariscv/isla/blob/f06371ffb420becb6d325772aeeaf2336276bd16/test/isarch/cli/solve-state/test_isarch_cli_solve-state.sh#L222)

这不仅是测试选样限制，也是 `solve-state` 执行压缩访存时尚未接全的一步：`rv64d.ir:287724–287725` 的 C_LD 返回 `ExecuteAs(LOAD(...))`，`:287800–287801` 的 C_SD 返回 `ExecuteAs(STORE(...))`；solve 只调用一次 `zexecute`，收到返回便收集结果。完整模型的外层在 `rv64d.ir:385190–385198` 遇到 ExecuteAs 会再次执行转换后的指令，而当前 solve 入口没有这样继续。通俗说，翻译完简写指令便结束，还未完成翻译后的读写动作。

分支收录的 `agents/memory_support_baseline.md` 开头明确为 **0008fae 改动前** 基线：

## 建议的后续顺序（未实施）

1. 补齐压缩访存转换后继续执行的流程，修正事件先后顺序，并用同一指令内至少两次访问验证。
2. 为普通内存建立按字节的重复读一致、写后读、部分覆盖规则；优先复用底层已留出的回调接口和既有 testgen 思路。
3. 把访问记录整理为“开跑前准备哪些字节”和“跑完后检查哪些字节”，明确未知值的选定方式及地址范围条件。
4. 将这两份数据接到实际测试程序，确保硬件与参考模型使用相同初始内容，核对修改后的字节。
5. 按单次真实读取、单次真实写入、重复/重叠访问、向量和特殊读写、跨界与异常逐层验证。涉及代码实现时另列可审阅计划，按根规则确认后实施。

现阶段可用于观察已经跑通路径的读写地址和数据，也适合继续开发；若目标是可靠生成和重放内存测试，前四项属于核心缺口。
