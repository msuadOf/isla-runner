## Summary

In Z3 4.16.0, adding an independent finite-enumeration constraint to a small floating-point formula makes the explicit `default` tactic substantially slower. Prepending `dt2bv` restores the faster behavior.

This is a performance/strategy-selection report, not a SAT/UNSAT correctness report. I am specifically testing `(check-sat-using default)`, not claiming the same results for every use of `Solver()` or plain `(check-sat)`.

## Minimal reproducer

Save as `enum-fp.smt2`:

```smt2
(declare-const x (_ FloatingPoint 8 24))
(declare-datatypes () ((Mode A B C D E F)))
(declare-const mode Mode)
(assert (= mode F))
(assert (fp.isNaN (fp.sqrt roundNearestTiesToAway x)))
(check-sat-using default)
```

The enumeration constraint has no dependency on `x`. The expected result is `sat`, which all completed runs produce.

Two controls:

1. Remove the `Mode` declaration, `mode` declaration, and `(assert (= mode F))`, leaving the floating-point assertion and `default` unchanged.
2. Keep the original formula and replace its last line with:

   ```smt2
   (check-sat-using (then dt2bv default))
   ```

## Measurements

Environment: Linux x86-64, Homebrew Z3 4.16.0 (`z3 -version`: `Z3 version 4.16.0 - 64 bit`). Each run was pinned to one CPU. Three repetitions per case were run on separate cores; the cases were run concurrently. No seed was explicitly changed.

Representative command, with a dedicated CPU and output file per run:

```sh
/usr/bin/time -f '%e,%U,%S,%M' -o resources.csv   taskset -c 100 timeout 65s z3 -t:60000 enum-fp.smt2
```

Wall-clock seconds, including process startup:

| Formula / tactic | Three runs (s) | Median (s) | Result |
| --- | --- | --- | --- |
| FP only / `default` | 0.109, 0.109, 0.109 | 0.109 | `sat` in all runs |
| FP + independent enum / `default` | 6.613, 16.028, 15.826 | 15.826 | `sat` in all runs |
| Same FP + enum / `dt2bv; default` | 0.308, 0.208, 0.209 | 0.209 | `sat` in all runs |

The exact timings vary, so I would not treat the ratio as a stable speedup. The notable behavior is that an otherwise independent enum constraint changes strategy selection and substantially increases runtime. I encountered the same pattern while investigating larger floating-point queries generated by symbolic execution; the example above does not require that application.

## Source investigation

In the 4.16.0 source:

- [`mk_default_tactic`](https://github.com/Z3Prover/z3/blob/z3-4.16.0/src/tactic/portfolio/default_tactic.cpp#L35) simplifies the goal and dispatches to `qffp` when `mk_is_qffp_probe()` succeeds.
- [`is_non_qffp_predicate`](https://github.com/Z3Prover/z3/blob/z3-4.16.0/src/tactic/fpa/qffp_tactic.cpp#L111) excludes datatype sorts, including finite enumerations.
- [`mk_qffp_tactic`](https://github.com/Z3Prover/z3/blob/z3-4.16.0/src/tactic/fpa/qffp_tactic.cpp#L80) performs floating-point preprocessing/translation before solving.

This appears to explain why a mixed FP/finite-enum goal misses that specialized path. In the larger queries, `is-qffp` fails after `simplify`, but succeeds after `simplify; dt2bv`.

I also inspected the corresponding source at master commit [`8fbb275aba0472e862e289c7af1331b3bd5d512c`](https://github.com/Z3Prover/z3/commit/8fbb275aba0472e862e289c7af1331b3bd5d512c). The relevant FP dispatch/probe behavior is still present. I have **not** built or benchmarked that commit, so the runtime measurements above apply only to 4.16.0.

## Question / possible improvement

Would it be appropriate for `default` to normalize eligible finite enumerations before classifying mixed floating-point goals, or otherwise recognize this restricted combination and select a suitable preprocessing pipeline?

I am not suggesting treating arbitrary recursive datatypes as QF_FP, or unconditionally adding expensive preprocessing to every goal. A targeted improvement would need to preserve enum bounds/model reconstruction and be checked against existing FP, BV, array, datatype, and incremental/assumption tests. I would be happy to follow guidance on the appropriate location and regression-test scope.
