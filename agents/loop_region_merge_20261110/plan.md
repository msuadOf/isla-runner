# 循环内分叉合并：设计稿与实施计划（2026-11-10，v3：补 M2）

v1 经 Codex 只读审核，本版按其“必须改”六项和大部分“建议改”修订。

## 结论

“遇到回边就放弃”在 V 浮点 clause 里大多是**误判**：分叉本身在一轮循环之内，但 Sail `assert` 的失败出口把汇合点拉到了函数出口，区域因此跨过回边。

修法分三层，按顺序做：

1. **M0 静态测量（先做，不改行为）**：在真实 IR 上统计每个被拒分叉按新规则能否变为无环，**以及能否通过现有合并预检**。
2. **M1 汇合点修正**：汇合点按“不以断言失败结束的路径”计算，同时让活跃性在变量重新声明处截断。两件事必须一起做，否则拒绝原因只是从“有回边”换成“状态不兼容”。
3. **M2 浮点辅助函数写 fcsr**：审核发现，FVFTYPE 修完回边后，区域里的 `fp_add` 等调用会触发 `accrue_fflags` 写 `fcsr`，预检直接以 `callee_state_write` 拒绝。也就是说，**对 V 浮点，M1 是必要条件但很可能不够，真正放开合并要靠 M2**。M2 比 M1 难，单独设计。

真正跨轮的合并（M3：循环出口多路合并或有界展开）成本最高，等 M0/M1/M2 的数字出来再定。

## 诊断

### 例子：FVFTYPE 的 `mask[i]` 分叉

```sail
foreach (i from 0 to (num_elem - 1)) {
  if mask[i] == 0b1 then {                       // ← pc28821，被拒 171 次（has_back_edge）
    result[i] = match funct6 {                   // ← pc28826/28833/…，每项被拒 56 次
      VF_VADD => fp_add(rm_3b, vs2_val[i], rs1_val),   // ← fp_add 内部写 fcsr
      ...
      VF_VSLIDE1DOWN => {
        let last_elem = get_end_element();
        assert(last_elem < num_elem);            // ← 失败出口直达函数出口
        if i < last_elem then vs2_val[i + 1] else rs1_val   // ← pc29115
      }
    }
  }
}
```

isarch 默认在加载时把断言改写成“条件跳转 + `Exit(AssertionFailure)` 尾块”（`assertions_to_jumps`，`src/isarch_main.rs:588`；只有 `--fork-assertions` 才不改写）。区域分析把这个尾块当作通往函数出口的正常出口，于是 `if mask[i]` 的直接后支配点变成函数出口，区域包含了整个循环和回边 pc29135→28810。

## 设计

### M0：静态测量

复用已有的真实 IR 测试接口（`regions_real_ir`，`isla-lib/src/ir/regions.rs:1090`：`DefParser`、`ir_lexer`、`FunctionRegions::with_options`、`region`、`cfg`），不初始化架构、不跑 isarch。

- 先对 IR 应用 `assertions_to_jumps`，与旧实测的指令形状一致；核对其他加载期改写造成的 pc 偏移。
- 对旧全量实测快照中每个被拒分叉，按入口 `function + branch_pc` 聚合（不用 `rejected_function + target_pc`），分别求现状区域和 M1 区域。
- 分类保留全部结果：现状已无环 / M1 后无环 / M1 后仍有环 / NoJoin / ExitsRegion / 非 Jump。
- 对“M1 后无环”的区域，再跑现有的静态合并预检（`region_merge.rs:336`，检查区域全部节点的被调函数效应），分成“可通过预检”和“被预检拒绝（原因）”。这一项决定 M2 的必要性。
- 按快照里的拒绝次数加权汇总到 clause。日志每条快照只列前 30 个位置，被截断的 clause 报告遗漏的权重。快照计数只是硬超时前的观测值。

### M1-a：汇合点按不以断言失败结束的路径计算

**语义依据**：
- 默认形态（断言改写为跳转）：推演臂走到 `Exit(AssertionFailure)` 时记为死臂（`region_merge.rs:595-610`）。`commit_dead_transaction` 撤销该臂事务，并加入“非该臂条件”的约束。存活臂的约束在提交时受臂条件保护。所以缩短汇合点后，**正常完成路径的可行域和结果关系不变**。
- 直接调用形态（`--fork-assertions`）：`optimistic_assert` 对符号条件只要可能为真就把条件加为约束继续，必然为假才报 `AssertionFailure`，同样记为死臂。推演中的符号悲观断言会拒绝整个推演（`SymbolicAssertion`），不受本改动影响。求解器返回 Unknown 或出错时也不会被当作断言失败。

**会变的统计**：普通执行中走到断言失败的路径会计入 `assertion_filtered_paths`（`src/isarch/exec.rs:1858`），进入输出和缓存摘要。区域内的死臂不经过这个计数，所以合并变多以后，这个计数会变少。它不产生样本，也不让摘要变成 partial。本设计**接受这个统计口径变化**，并在结果里注明。如果你要求保持该计数不变，执行层就需要额外记账，请在审核时指出。

**图的使用边界**：

| 分析 | 当前使用的图 | M1 之后 |
| --- | --- | --- |
| 后支配、区域闭包、`validate_region` | `FunctionAnalysis.cfg` | 用新的“断言过滤”视图 |
| 活跃性传播、区域外边界读取、声明位置 | `FunctionAnalysis.full_cfg` | 不变，保留完整边 |
| `always_terminates`、`reachable_instructions`、传递效应上界 | `region_summary` 单独建的 `RegionCfg` | 不变，保持保守 |

新选项放在 `RegionOptions` 里，默认关闭，只有区域查询启用。这样 `always_terminates` 这类对后继做全称判断的分析不会因为空后继得出错误证明。

**落地要点**：
- 断言过滤视图里，`Exit(AssertionFailure)` 不再连到函数出口，成为死端。
- 区域闭包构造（`compute_region`，`regions.rs:587`）要改：从入口出发的可达闭包**必须保留实际执行会经过的失败尾块指令**，否则执行器走到这些指令时会报 `RegionEscaped`。
- 只允许以 `Exit(AssertionFailure)` 结尾的块作为死端。其他无后继的情况（显式 `Exit`、`MatchFailure`、不终止）一律保持现状。`MatchFailure` 不过滤：它在执行器里是独立错误，会记入 errors、让摘要变成 partial。
- 失败尾块内部仍按原规则拒绝环和其他出口。
- 保留现有保护条件：`address_taken` 的全函数排除，所有声明位置都在区域内才可删除，不删 `RETURN`，基态已有的槽位不删（`region_merge.rs:807`）。

### M1-b：活跃性在重新声明处截断

**现状**（`regions.rs:532` 附近）：`live_in = 读 ∪ ⋃ live_in(后继)`，从不截断。

**改为**按“槽位用途”计算：

```
live_in(pc) = 用到槽位的名字(pc) ∪ (⋃ live_in(后继) − 本指令重新建槽的名字(pc))
```

- **用到槽位**：读取这个名字，以及需要已有槽位的写入（普通赋值 `Copy`、字段或元素写）。审核指出，普通赋值在目标不在局部表时会被当作寄存器写，非寄存器时会 panic（`executor.rs:793`）。所以汇合后、下一轮重新声明前如果有赋值，这个槽位必须保留。
- **重新建槽**：`Decl` 会重新插入槽位；`Init`（`名字 : 类型 = 表达式`）先求右侧再建槽，所以右侧读到的名字照样算“用到”，包括读它自己的情况。
- `Decl` 会清理当前调用作用域的 `initial_variables` 项。初值提升只针对基态已有的未初始化槽位，不受影响。没有发现闭包捕获之类绕过的读取途径，显式引用由 `address_taken` 保护。

**例子**：循环体里一臂声明并使用临时变量 `t`，下一轮在使用前又 `Decl t`。按新规则，`t` 在本轮汇合处不活跃，可以丢弃，两臂就能合并。如果汇合后紧接着有 `t = …`，`t` 仍活跃，保持现状。

**影响面**：规则对所有函数生效。但直线代码里，区域外的同名声明已经会阻止删除，所以不保证每个 clause 的合并都增加。

### M2：区域内读写全局状态的通用合并（v3 新增，2026-11-10）

用户要求通用机制，不为 fcsr 开特例。事实依据见 [m2-facts-20261110.md](m2-facts-20261110.md)（Codex 只读调查）。

**现状**：合并本身已经能处理寄存器和全局 let。每臂在自己的帧副本里读写，汇合时把两臂写过的寄存器按臂条件合成 ite（`region_merge.rs:857`），合并后按写入顺序补发整寄存器 `WriteReg`。真正挡路的是四条访问规则：

| 规则 | 位置 | 对 `accrue_fflags` 的影响 |
| --- | --- | --- |
| 只有区域入口那一层可以写全局，被调函数不能写（`CalleeStateWrite`） | `region_merge.rs:136`，静态摘要 `region_summary.rs:185` | `fcsr = …` 在被调函数里，直接拒绝 |
| 同一寄存器在区域内只能写一次（`RepeatedRegisterWrite`） | `region_merge.rs:143` | `mstatus` 先写 FS 再写 SD，两次写 |
| 已读过的寄存器不能再写（`RegisterReadWrite`） | `region_merge.rs:147` | 先读 `fcsr` 再写回 |
| 有过任何寄存器写之后不能再读任何寄存器（`RegisterReadAfterWrite`） | `region_merge.rs:49` | 写完 `fcsr` 又读回给回调 |

此外，两臂共同读过的寄存器，读取序列（次数和顺序）必须完全一样（`RegisterSequence`，`region_merge.rs:886`）。`accrue_fflags` 只在标志变化时才写回，所以一臂“读、写、读”，另一臂“读、读”，序列对不上。

代码注释写明，合并后的主迹对寄存器读只保证“前态和访问足迹”，不保证逐条读写顺序（`merge_record.rs`、`merge_enumeration.rs` 头注释）。isarch 的样本前态取初始寄存器，后态取最终帧，都不靠事件时间线重放（`src/isarch/samples.rs:174`）。所以这四条规则比它要保护的东西更严。

**做法：把臂内的寄存器读分成两类**

- **前态读**：本臂还没写过这个寄存器，读到的是区域入口时的值。照旧记录足迹、发布 `ReadReg`。
- **内部读**：本臂已经写过这个寄存器，读到的是自己刚写的值。这个值已经由 SMT 定义表达清楚，不是前态，所以**不记足迹、不发事件**。

在这个区分上放宽规则：

1. **被调函数可以写全局**：去掉“只有入口层可写”的限制，动态检查和静态摘要都去掉。写寄存器和写全局 let 都是写当前臂的帧副本，与调用深度无关。通过引用或地址写（`Loc::Addr`）仍然拒绝。
2. **可以重复写**：只有最终值参与合并。写序列按每个寄存器第一次写的位置记录。
3. **读后写、写后读都允许**：写后读按内部读处理。
4. **前态读按足迹去重**：同一臂里对同一个 `(寄存器, accessor)` 的第二次前态读不再记录，因为非 relaxed 寄存器在写之前两次读到的值相同。两臂的足迹合并时：
   - 两臂都读过的，条件取 OR；
   - 只有一臂读过的，按现有 `single_arm_reads` 记录；
   - 顺序像写序列一样做拓扑合并，冲突时拒绝。

   这样“读、写、读”和“读、读”两臂的足迹都变成 `[fcsr]`，可以合并。

5. **保持不变**：relaxed 寄存器和带历史写入的寄存器仍然拒绝（`region_merge.rs:860`）；内存写、设备读、`StateEffect` 预检不变；`MatchFailure`、未知外部函数到达即拒绝也不变。

**例子**：`if mask[i]` 两臂都调用 `fp_add`。
- 一臂：标志变化，读 `fcsr`、写 `fcsr`、写 `mstatus` 两次、再读 `fcsr`。
- 另一臂：标志没变，读 `fcsr`、再读 `fcsr`。
- 合并后：`fcsr = ite(c, 新值, 原值)`，`mstatus` 同理；足迹是“两臂都读了 `fcsr`”，后面统一补发 `WriteReg fcsr`、`WriteReg mstatus`。

**开关**：给区域合并加一个选项，默认关，isarch 在 path merge 下打开，与 M1 的选项一起。旧测试在关闭时保持原断言，新测试覆盖打开时的行为。

**代价与风险**：
- 合并路径的 trace 里，内部读和重复的前态读不再出现。`RegisterReadAfterWrite` 原本保证的“读事件全在写事件之前”，在新规则下由“内部读不发事件”保证；不同寄存器之间的相对顺序本来就不保证。
- 依赖精确事件顺序的使用者，比如多线程公理模型，不应该开这个选项。所以它默认关，只在 isarch 打开。
- 进入嵌套区域后，外层臂读一个只在内层某一臂被写过的寄存器，算内部读，读到 ite 值。这时另一种情况下的前态值不会进足迹。isarch 的前态是全符号的初始寄存器，不受影响；需要用测试确认 path cache、DAG 导出不依赖这部分足迹。
- 调查同时发现，`fp_add` 的数值后端 `riscv_f32Add` 等在 IR 里只有声明，没有实现，和 31 个“浮点函数不存在”的快速失败是同一个来源。M2 放开合并后，V 浮点有可能更早走到这些调用，届时如实记录。

**测试**（TDD）：
- 被调函数写寄存器、写全局 let，合并成功，最终值是 ite；
- 同一寄存器写两次；读后写；写后读不产生 `ReadReg`；
- 一臂“读写读”、一臂“读读”，可以合并；
- 两臂读不同寄存器顺序相反，拓扑合并成功；顺序成环时拒绝；
- relaxed 寄存器仍然拒绝，`Loc::Addr` 写仍然拒绝；
- 选项关闭时旧测试全部不变；
- 差分：合并开/关返回关系、路径覆盖相同，最终寄存器映射在每条路径上等价。差分框架要补上最终寄存器比较。

### M3：真正跨轮的合并（暂不做）

| 方向 | 做法 | 主要难点 |
| --- | --- | --- |
| A：循环出口多路合并 | 不同轮次退出循环的路径在出口按“第几轮退出”做 N 路合并；可复用 `merge_val_nary`（`primop_util.rs:737`） | 循环变量（I64）不同时现有值合并会拒绝；普通 checkpoint 要求事务深度为 0（`smt.rs:3065`）；需要出口会合机制；记录结构可能要改成 N 路 |
| B：有界展开 | 已知上界 K 时按 K 轮展开成无环区域 | 节点身份只有原始 pc；K 必须是语义上界（FVFTYPE 为 64）；K=64 超过嵌套深度 16；步数预算会被放大 |

FVFTYPE 的循环次数只由 SEW/LMUL 决定，取值很少，所以循环头本身的分叉有限，爆炸主要在循环体内。M3 是否需要，以 M0/M1/M2 的结果为准。

## 不变量与格式

- M1 不改 `RegionMergeRecord`（仍是 Root/Then/Else）、FastFacts、DAG、路径缓存格式，缓存 schema 不升版本。
- M1 会改变合并结果，已生成的缓存内容对受影响 clause 会过时，需要重新生成。新缓存放在独立目录，并注明来源版本，避免读到旧缓存而掩盖效果。
- M3 若改为 N 路 arm，要同步改 `merge_record.rs`、`merge_enumeration.rs`、FastFacts、DAG、路径缓存，并升 schema 版本。
