# CPU 功能 fuzzing：微架构反馈量与创新性边界

日期：2026-10-23。范围：文献核实与候选设计；未修改生成器、DUT 或执行反馈接口，未运行新实验。用途是本地 CPU 功能验证。本文接续[反馈综述](coverage-feedback-review.md)，补充“除了寄存器／MUX／FSM／CSR，还能反馈什么”。[来源和证据等级](microarchitecture-feedback-sources.json)。

## 1. 两个前提

RTL 是观测来源，不是唯一一种反馈抽象。同一批 RTL 信号可以形成单点命中、资源占用、联合状态、事件先后与间隔、逐指令生命周期、数据来源关系。反馈量也可以是目标分数，不必有可枚举的覆盖率分母。

Sail-RISC-V 提供 ISA 语义，但不自动保证生成物已经遍历 ISA corner。必须区分模型描述完整、符号执行实际探索到路径、每条路径采到代表性值、序列及上下文交互得到覆盖。即使某些 ISA 语义条件已覆盖，同一条件也可能通过不同微架构路径实现。因此可以把研究重点放到 DUT 行为，同时保留实际执行的语义标签。

## 2. 相关工作的反馈及角色

| 工作 | 实际反馈／观测 | 动机及用途 | 证据和限制 |
| --- | --- | --- | --- |
| DRVFuzz，USENIX Security 2026 | 动态指令状态 `σ=(opcode, 满足的语义谓词集合)`，反馈相邻指令的有向转移 `τ=(σ_k→σ_{k+1})` | 保留新转移种子，覆盖数据敏感条件之间的有序交互 | 官方全文 §4.3、§6.4。标签来自操作数和架构上下文，是微架构行为代理，不是实际 ROB／LSQ 状态。RTL branch／toggle 是其评测量。 |
| DiveFuzz，CCS 2025 | 作者实现说明以动态多样化的指令写回值驱动 CPU 状态探索 | 使指令生成超越 opcode 多样性 | 作者仓库 README；未取得出版方全文，不能据此断言具体反馈键、分桶或收益数值，也不能将写回值称为直接微架构覆盖。 |
| SurgeFuzz，ICCAD 2023，技术前史 | Surge score；实现目标包括 LQ／SQ／replay queue 使用、MSHR busy、scheduler stall、store blocked、异常密度等 | 定向施加资源压力，探索高负载及阻塞场景 | 作者实现 README 核实。队列占用、事件密度和持续时间作为目标已有明确先例；不报告未核实的收益数字。 |
| DejaVuzz，ASPLOS 2025 | 每周期按模块记录被标记寄存器数量，覆盖键为 `(module, tainted-register-count)` | 把内部数据传播压缩成位置不敏感的反馈，减少不同存储槽位造成的冗余 | 全文 §4.2.2。原目标与本地功能检错不同；可借鉴数据来源抽象，不能直接沿用判错逻辑。 |
| Coverage-Guided Pre-Silicon Fuzzing…，2025 预印本 | 两份 DUT 每周期寄存器差异向量 `Δ` 的相邻转移散列，即 SCD feedback | 引导两次执行内部差异的演化；反馈确实进入 seed／mutation 循环 | arXiv:2511.08443v2，§III-C。原目标不同；差异本身不等于功能错误。 |
| Sonar，MICRO 2025 | 综述列为争用点 request interval 的评分 | 将资源争用时序变成搜索目标 | 正式会议条目核实；反馈描述目前来自 2026 SoK 表2，未读到原论文全文，不能给出精确公式和独立效果结论。 |
| WhisperFuzz，USENIX Security 2024，技术前史 | Micro-Event Graph／Path；用 SVA cover properties 监测事件路径和时序覆盖 | 从内部事件路径解释和监测时序行为 | 全文 §3.4、§3.8。seed generation 使用既有 coverage-feedback fuzzer；不能将其全部阶段说成由 MEG 在线反馈统一驱动。 |

DRVFuzz 在六款 CPU、每款 24 小时的作者实验中报告 22 项新问题，其中两项是构建／配置问题，不能全部称作 RTL 功能 bug。其消融报告：完整版本 22、无语义模型 8、无转移引导 15、只按单个 mode 反馈 18。因此有序语义交互确实比单独命中 mode 多发现四项；这不是把 22 项全部归因于覆盖率。

这也限制了创新性表述：“语义 corner 两两转移”“高队列压力”“双副本差异”“事件路径”都已有先例。

## 3. 候选量：定义、目标和既有基础

下表的“候选贡献”只表示值得研究。尚未找到同定义工作不等于已完成查新。传统硬件验证的 covergroup、cross coverage、transition bins 和 SVA 已包含很多基础形式。

| 候选量 | 一个可实现的反馈键／目标 | 希望探索的功能风险 | 既有基础与创新性判断 |
| --- | --- | --- | --- |
| 资源压力的联合情境 | `(ROB占用桶, LQ占用桶, MSHR占用桶, replay/flush事件)`；另记有界连续阻塞长度 | 多资源同时紧张时的反压、分配释放和恢复 | 单项压力已有 SurgeFuzz；联合 coverpoint 属于常见 DV 方法。适合作基线，单独创新性低。 |
| 同指令／事务的事件关系 | `(语义类别, 事件A, 事件B, 先后关系, 时间差桶, 相对年龄桶)` | 异常、提交、重放、取消之间的竞态 | 事件时序已有 WhisperFuzz 等；DRVFuzz 已有语义转移。跨层自动关联并用于求解反馈是候选贡献，单纯记录先后不是。 |
| 实际数据来源／转发关系 | `(producer类, consumer类, 实际来源, 年龄距离桶, 地址重叠类, byte-mask类)` | 错源转发、部分写覆盖、旧值使用、取消后仍被消费 | 不同于仅观察数值或静态 def-use；与 DejaVuzz 数据流抽象及传统 DV 有联系。低成本、可迁移的在线来源关系反馈是候选贡献。 |
| 指令／微操作生命周期片段 | 对 `allocate→issue→execute→replay→writeback→commit/squash` 的短路径或局部图去重 | 重放后漏唤醒、重复完成、flush 后残留、资源泄漏 | 路径和 transition coverage 已知。跨模块关联、身份归一化及有界片段选择可能形成贡献；直接散列完整 trace 不足以成立。 |
| 语义条件下的微架构实现路径 | `(Sail语义标签, 上述事件／来源／生命周期特征)` | 同一 ISA 条件在不同内部实现情境下的错误 | 与 DRVFuzz 最需区分：这里观测实际内部事件，而非相邻指令的语义状态对。自动提取及约束保持闭环是较值得研究的组合。 |
| 进展／恢复行为 | `(未完成工作类别, stall原因, 连续无进展桶, flush→恢复间隔桶)` | 死锁、丢唤醒、恢复停滞、资源不能回收 | stall／busy 持续时间已有 SurgeFuzz；watchdog 与性能验证也常见。应作辅助目标，单纯“运行越慢越好”创新性低。 |
| 向量访存子事务的交互 | `(语义标签, 拆分形态, lane/segment关系, 完成顺序, fault/replay/cancel组合)` | 部分完成与异常、掩码与提交、segment 子访问取消等交互错误 | 向量 functional coverage／事务验证有既有基础；本轮未找到精确同定义的通用在线指标。自动从模型关联内部事务值得查新，不应把枚举 lane 当作创新。 |

数据来源举例：同一条 load 的最终数值相同，但可能来自 D-cache、较老 store 的转发、多个 store 的字节合并或 refill。只按写回值反馈会合并这些情况；按实际来源关系反馈可以区分。必须采集真实 mux/握手选择结果，不能只由 ISA 操作数推断。

生命周期和时序需将事件关联到同一动态指令或事务。原始 ROB、物理寄存器和 LSQ ID 会循环复用，应结合代次和相对年龄归一化。不同指令上孤立发生过两个事件，不能计成同一条指令经历了该事件对。

## 4. 一个具体时序例子

DRVFuzz §3 的 BOOM-V4 例子中，两条非对齐 store 的异常与 ROB retirement 协调不同。Store A 的异常在到达 ROB head 时已可用，提交正确被抑制；Store B 的异常检查较晚，错误地先产生 commit-valid，再异常 flush。这里采用论文的根因解释，不把时序事件自行当作错误判据。

可以抽象采集：

```text
K = (store-misaligned,
     order(exception-available, ROB-head/commit-arbitration),
     bucket(relative-cycle-gap),
     store-buffer-pressure-bin,
     recovery-kind)
```

`ROB-head` 和具体 commit arbitration 采样时刻要按 DUT 的时钟／握手定义；同周期不同组合逻辑依赖不能被周期计数自动区分。RTL adapter 应给出事件语义。`K` 仅用于探索，真正判错仍依赖参考语义、断言或有明确假设的进展检查。

另一种候选是成对上下文扰动：保持 payload 的指定 ISA 前态和预期行为，改变前导指令造成的 cache／依赖／资源情境，再比较内部特征。这与 SCD 的双执行思路有联系，不能宣称成对执行新颖；还需保证前导指令未破坏指定语义条件。差异本身不是 bug。

## 5. 对 Isla 路线的建议

优先研究“语义条件下的事件关系与数据来源”，保留结构覆盖、压力桶作为对照。理由是 bug 往往依赖某个 corner 在特定内部情境下发生，而非仅依赖某个信号首次翻转。

可讨论的闭环是：Isla 生成并保持目标语义条件；变异前导指令、依赖和地址关系；DUT 反馈实际事件特征；保留新特征种子；必要时再向 Isla 请求联合修复操作数和上下文。本阶段尚未实现；尤其不能宣称 Sail 能直接求解 DUT 内部周期关系，若没有 RTL 约束模型，它只能用语义约束配合具体执行搜索。

创新应落在具体方法和证据：自动提取哪些跨层条件、如何关联动态事务、如何控制状态空间、怎样低成本反馈给变异与求解，以及同预算是否增进真实检错。简单添加 `(semantic, event, bucket)` 的 hash 并不充分。

实施前需核对 DUT 的可观测接口。只看 retire trace 会漏掉未退休指令、replay 和 squash。短程序若每次重新初始化内部状态，也可能消除目标情境。原始 ID、全宽值和完整 trace 会制造大量无效 novelty；宜用有界片段、分类与桶，保留少量诊断原始 trace。

后续比较必须固定时间／仿真预算、程序长度和初始化方法；比较结构覆盖、单项压力、语义转移与候选关系量的消融。不能只报告自己定义的指标上涨。当前仍为文献讨论，没有新增实验或检错结论。
