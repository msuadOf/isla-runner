# CPU 功能测试与软件 fuzzing：反馈覆盖的选择与符号执行闭环

日期：2026-10-22。本阶段按用户要求建立文献知识体系，不推进本项目指标选型、实现或实验。本项目定位为本地 CPU 功能验证与 bug 检测。下文涉及其他验证目标的工作，仅说明反馈抽象方法，不把其判错目标迁入本项目。

主范围为 2025–2026 年公开工作。正式出版年份与预印本年份分别说明；早期论文只用于解释技术来源。全部效果为作者报告，本轮没有复现实验。来源及阅读范围见文末和 [来源清单](coverage-feedback-sources.json)。

## 1. 覆盖率、反馈和判错是不同层次

一个候选输入 x 经过目标执行得到轨迹 T(x)。反馈首先做特征提取与抽象，得到特征集合 F(x)。例如 F(x) 可以是执行过的边、def-use 对、抽象状态转移或输出类别。相对已见集合 C，新颖性是 F(x) − C。实际测试器还可使用命中频率、到目标的距离和单位时间收益决定保留、父种子选择、变异次数和求解任务。

| 层次 | 回答的问题 | 例子 |
| --- | --- | --- |
| 验证目标 | 希望发现哪类错误？ | 指令结果错误、访存错误、状态更新错误 |
| 观测来源 | 能看到哪里？ | 软件插桩、RTL 信号、架构状态、算法输出 |
| 特征与抽象 | 什么差异算不同？ | 边ID、定义—使用对、状态分桶、转移序列 |
| 聚合／奖励 | 怎样定义收益？ | 新点数、稀有点权重、模块权重、距离下降 |
| 搜索动作 | 收益影响什么？ | 保留样例、分配变异次数、选择求解分支 |
| 判错器 oracle | 本次是否发现错误？ | 与参考模型的结果／状态差异、断言失败 |
| 评测指标 | 最后如何判断方法有效？ | 留出 bug 命中率、首次命中时间、独立根因数、成本 |

反馈不一定是百分比。许多测试器只知道已见特征数，不知道可达特征的精确分母。到目标的距离和求解可满足性也可以是反馈，但不是覆盖率。输入去重数、随机取值数不能自动等同为行为覆盖。

必须区分三件事：论文为决策采集了什么、用什么打分、最后在图表里报告了什么。改进 RL 或 bandit 不意味着提出了新覆盖率；报告 MUX 覆盖也不意味着用它指导变异。

## 2. 从通用结构覆盖出发

软件边覆盖用基本块转移近似执行行为，收集便宜、无需手写业务规范，适合高吞吐测试。命中次数分桶能区分部分循环行为，但仍不能表示所有路径、数据状态和执行顺序。

硬件并发、时钟和流水线使“走过代码”与“经历状态”分离。编译后仿真器的软件边、RTL 分支、MUX 选择、时钟寄存器状态、架构 CSR 状态是不同观测层。尤其内部 control register 不等于 RISC-V 架构 CSR。

| 反馈家族 | 希望近似覆盖什么 | 主要信息损失 |
| --- | --- | --- |
| line／基本块／edge／branch | 哪些结构位置或控制转移被执行 | 同一路径不同数据状态被合并 |
| condition／expression | 条件求值或逻辑组合 | 语义和组合定义依工具而异，不自动证明完整功能 |
| toggle／MUX | 信号变化、选择行为 | 大量数据位变化可能与目标无关；不一定保留时序上下文 |
| control-register／CSR 状态 | 内部控制或架构配置状态 | 单状态不一定保留形成过程；粗细需另外定义 |
| def-use／value-flow | 数据从哪里产生、在哪里消费 | 仅有静态关系不保证真实运行依赖；数值仍可能被合并 |
| 抽象状态／转移／路径前缀 | 同一位置的不同上下文及顺序 | 状态／路径数量膨胀，需限制历史和粒度 |
| 语义／算法输出特征 | 输入造成的可解释行为差异 | 需要领域知识，抽象过粗会漏差异、过细会膨胀 |
| 目标相关评分 | 是否接近指定位置或条件 | 图上接近不一定可行，也不保证数据条件满足 |

这些是并行发展路线，并非一种新指标按年份替代所有旧指标。

## 3. CPU 论文：反馈点保持不变，优化它的使用方式

### GenHuzz（USENIX Security 2025）

[正式论文](https://www.usenix.org/system/files/usenixsecurity25-wu-lichao.pdf)，重点 §3.2、§4.1、§5、§7。

- **出发点**：随机指令难以形成有意义的依赖；传统反馈通常只筛种子，未充分更新生成策略。
- **实际反馈**：VCS 收集 FSM、condition、line coverage；奖励还包含 token／指令有效性和 bonus。不是单一新覆盖定义。
- **闭环**：生成指令 token → 仿真得到反馈 → actor/scorer 更新 → 改变后续指令分布；覆盖停滞还参与模型重置。
- **希望覆盖**：RTL 的状态机、逻辑条件和代码结构，同时提高有效指令与跨指令组合。
- **效果与归因**：作者报告更高覆盖、更少测试及新问题；主要证明完整生成／奖励框架的收益，不能把全部收益归因于 FSM 或某一覆盖率。

### GoldenFuzz（NDSS 2026，预印本 2025-12）

[官方页](https://www.ndss-symposium.org/ndss-paper/goldenfuzz-generative-golden-reference-hardware-fuzzing/)、[全文](https://arxiv.org/html/2512.21524v1)，重点 §III-B、III-D、IV-B、VII。

- **出发点**：RTL 执行昂贵，生成的程序又容易过早失效，需要先用便宜反馈改善输入质量。
- **两阶段反馈**：GRM 阶段按参考模型判断的测试有效性改进生成；DUT 阶段用 VCS 的 FSM／condition／line coverage。GRM 有效性不是 RTL 覆盖，也不是符号执行。
- **奖励变化**：对块的覆盖作局部与跨测试评分，重复常见点降权；把高分与低分块组成偏好对，更新生成模型。
- **希望覆盖**：有效串接指令后的较深结构行为，避免预算消耗在早期失败输入上。
- **效果与归因**：作者报告 Rocket／BOOM／CVA6 上的覆盖和计算成本改善及五项新问题，并另报商业扩展两项。反馈阶段、块结构和学习方法共同变化，不能据此证明参考模型覆盖足以代替 DUT 反馈。

### ReFuzz（NDSS 2026，预印本 2025-12）

[官方页](https://www.ndss-symposium.org/ndss-paper/refuzz-reusing-tests-for-processor-fuzzing-with-contextual-bandits/)、[全文](https://arxiv.org/html/2512.04436v2)，重点 §IV、V、VI-C 及附录G。

- **出发点**：已有高质量测试能复用，但同一测试在早期和平台期价值不同。
- **实际反馈**：主实验使用 RTL branch coverage；当前累计覆盖所处档位作为 contextual bandit 的 context，新增覆盖为 reward。附加实验也把 condition coverage 作为实际目标重跑，并非只离线画图。
- **闭环**：按当前阶段选旧测试 → 结合已有 fuzzer 运行／变异 → 收到新增覆盖 → 更新选择策略；预处理还按覆盖矩阵移除冗余测试。
- **希望覆盖**：已有测试擅长的不同设计区域及后期剩余角落。
- **效果与归因**：作者报告最高 9.33% 的总覆盖增加和较大达到同等覆盖的速度提升。核心改变是复用与选择策略，不是新定义 branch coverage。速度倍数还受基线种子、配置及失效测试影响。

### HiFuzz（2026 预印本，作者标注 ITC 2026 接收）

[全文](https://arxiv.org/html/2607.06619v1)，重点 §III-C–E、V-A、V-B、V-E；会议接收仅按作者标注，未独立核对会议页。

- **出发点**：全局总覆盖会让容易增长的模块占据奖励，难模块被忽视；稀疏硬件奖励又不利于学习。
- **实际反馈**：按模块聚合 line／toggle／MUX／control-register 指标，用历史收益与剩余未覆盖程度动态调整模块权重；另有基本块编码的语义新颖度作为内在奖励。
- **闭环**：程序级策略安排布局，块级策略安排分布，受约束生成器填指令，实际覆盖和语义新颖度更新策略。
- **希望覆盖**：分散在各模块中的剩余行为，减少停留在易得覆盖上的局部最优。
- **效果与归因**：作者在 Rocket 的 24 小时实验中报告 control-register coverage 比 Cascade 高 48.9%；其 Encarsia 实验报告 30/60 对 Cascade 26/60。两者均是完整系统结果；编码器训练成本与在线预算口径应分开看。嵌入距离是学习到的代理，不是实际硬件状态覆盖。

## 4. CPU 论文：改变抽象或检验覆盖的有效性

### Encarsia（USENIX Security 2025）

[正式论文](https://www.usenix.org/system/files/usenixsecurity25-bolcskei.pdf)，重点 §8.1–8.4。

作者先研究 177 个真实 CPU bug，构建可自动注入、经形式方法确认有架构可观测效果的 bug 集。这样可以在同一批 bug 上比较测试器。

其控制实验发现，DifuzzRTL 和 ProcessorFuzz 开启／关闭各自覆盖反馈时命中的 bug 集相同；另一些比较中，黑盒生成能更快触发相同 bug。种子和判错方式也是重要变量。

这不是“所有覆盖无用”的证明。它的证据范围是特定测试器、反馈、CPU 和注入 bug 集。但它直接要求：覆盖选择必须经检错与成本对照验证，不能从覆盖曲线上涨直接推出有效。

### SimFuzz（2026 预印本）

[全文](https://arxiv.org/html/2601.11838v1)，重点 §III、IV。

从历史 bug 种子出发，尽量保持控制转移，以指令类型、opcode、子语义、字段相似性指导块内变异。该方法不依赖覆盖反馈；MUX／toggle 是论文用于评价生成测试的指标。作者报告 17 个 bug、14 个此前未知。

它展示另一种取舍：当覆盖代理不充分时，可以用有价值的种子结构和领域启发式探索。不能说它选择了“MUX 反馈”或证明所有无覆盖方法更优。

### 专用抽象的例子：DejaVuzz 与 SCD

它们的验证目标与本项目的 CPU 功能正确性不同，仅用来理解反馈设计。

[DejaVuzz（2025）](https://arxiv.org/html/2504.20934v1) §4.2.2 记录 `(模块, 一个周期内被污染寄存器的数量)`，而非具体哪几个缓存／寄存器槽位被污染。同一传播行为落在不同位置会被合并，减少重复编码；覆盖增量影响继续变异还是放弃当前种子。作者报告相对 SpecDoctor 的 4.7 倍覆盖改善，指其专门定义的覆盖，不是通用 RTL 覆盖。

[SCD（2025 预印本）](https://arxiv.org/html/2511.08443v2) §III-C 将同一设计两次执行的内部寄存器差异构成 deviation vector，散列相邻周期向量为转移反馈。稀有／独特特征用于加权选样。§V-C 的 100 次实验中 weighted feedback 的首次命中中位数为279，相比 new-coverage 的326；两者差异的 p 值为0.220，不能宣称显著胜过普通新覆盖。与较弱的 Pass Feedback(100) 组比较为 p=0.003。它说明专用指标仍需要合适的对照与统计。

## 5. 通用软件论文：数据、语义、可观测性与目标相关反馈

### GraphFuzz（2025 公开预印本）

[论文](https://arxiv.org/pdf/2502.15160)，重点 §3.1.4、§3.2、§4、§5。

- **出发点**：一些图算法用少于十个图就能覆盖大部分代码，后续大量不同图不会获得新颖性信用。
- **实际反馈**：算法输出的低维摘要。例如强连通分量问题使用 `(分量数, 最大分量大小)`；最短路使用路径长度；最小生成树使用总权重与节点数，并对权重分桶。
- **覆盖意图**：不同的问题实例结构和算法行为，而不只是代码位置。
- **闭环**：变异图 → 执行并取输出摘要 → 新摘要保留为种子；分别测试纯代码覆盖、语义与代码组合、仅语义、无反馈。
- **效果**：两种语义变体能更快重现纯覆盖版发现的六个 bug；扩大测试后累计12个此前未知 bug，其中6个逻辑错误。不是所有输出摘要都有效，论文明确要求轻量、能区分行为、粒度适中。

### SPFuzz／SPFuzz++（USENIX Security 2025）

[正式论文](https://www.usenix.org/system/files/usenixsecurity25-xiao-jifan.pdf)，重点 §4–6。

- **出发点**：二进制软件缺源码，完整指令插桩可能慢、脆弱或不可用；选反馈要考虑可获得性和成本。
- **实际反馈**：系统调用事件及经过筛选的参数形成 N-gram 模式，以短窗θ、较长窗2θ、全轨迹模式组合；过滤不稳定参数，降低同一输入重复执行产生的噪声。
- **覆盖意图**：程序的功能单元和调用上下文；它是内部路径的代理，无法区分所有具有相同外部交互的内部行为。
- **效果**：作者报告最高45倍执行加速，平均分支覆盖相对二进制基线最高提高10.3%。反馈为系统调用模式，分支覆盖是独立评测结果。这里系统调用是本地程序运行观测，不代表网络交互。

### HF-DGF（2025 预印本，2026 TSE 出版元数据）

[全文](https://arxiv.org/html/2506.23063v1)、[出版标识](https://doi.org/10.1109/TSE.2026.3701683)，重点 §III、IV、VI。

- **出发点**：测试到达目标附近仍可能不满足触发错误的数据条件；只看图距离容易奖励无效接近。
- **实际反馈**：控制流距离、value-flow influence score、目标相关 slice coverage；静态分析给出相关性和权重，运行轨迹累积相关分数。
- **闭环**：距离影响种子优先级，三类反馈共同影响变异次数；只给相关区域插桩以降低成本。
- **效果**：41个已知目标的测试中，作者报告比 AFLGo 快5.79倍完成错误重现；有独立消融。距离和 influence 是分数，不是覆盖率；它也没有在主循环中使用 SMT，仅因名称含 hybrid 不能称为符号执行混合测试。

### FuzzRDUCC（2025 预印本，初步结果）

[全文](https://arxiv.org/html/2509.04967v1)，重点 §III–V。

用 angr/VEX 和 reaching-definition 分析从二进制预先提取 def-use 关系；QEMU 运行时将观察到的关系映射到 AFL++ 位图。它希望区分同一代码块下的数据来源／消费关系。

这是“符号／静态分析帮助设计反馈”，不是“运行停滞后每次在线求解新种子”。它的关系来自近似分析，不能把静态可达关系当成已验证动态依赖。初步结果未普遍胜过 AFL++ 的 crash 数，不能因反馈更细就宣称全面有效。

## 6. 符号执行接入循环的几种架构

| 工作 | 求解／分析对象 | 何时介入 | 返回什么 | 覆盖反馈承担的角色 |
| --- | --- | --- | --- | --- |
| FuSS，2025 | RTL＋testbench 经 Verilator 生成的仿真程序，angr/VEX/Z3 | 覆盖平台期 | 可接到已到达前缀后的输入后缀 | 检测停滞、选择已覆盖到未覆盖边界、具体执行核实收益 |
| SysFuSS，2026预印本 | QEMU 全系统固件，angr/Z3 | 边覆盖平台期 | 从中间状态到新区域的相关输入 | 停滞检测、前沿选择及回库 |
| S²F，2026预印本 | 软件源程序的 LLVM／SymCC 符号版本 | 与 fuzzer 协作的 coordinator 持续调度 | 翻转分支的解或多个采样候选 | 保留路径上下文、估计难度与后续收益、分配求解／采样 |
| ColorGo，2025预印本 | LLVM 编译插桩后的软件程序 | 执行偏离目标可达子图时 | 将执行纠回目标方向的新输入 | 可达性＋可行性过滤；目标到达为主，不追求全局新边最大化 |
| FuzzRDUCC，2025预印本 | 二进制分析 | 主要在预处理阶段 | def-use 元数据 | 定义 fuzzing 运行时位图，而非提供在线求解任务 |

### FuSS：复用已走到的状态，求短后缀

[作者公开全文](https://www.cise.ufl.edu/research/cad/Publications/tecs25.pdf)、[正式出版DOI](https://doi.org/10.1145/3760529)，重点 §3.1–3.5、5.1、5.3、5.4。本轮已找到全文；前一轮“仅核实摘要”的限制不再适用于这些章节。

1. RTL 与 testbench 转为 cycle-accurate 软件模型，改造 DifuzzRTL 生成／变异指令字节数组。
2. 监测滑动窗口中的新增覆盖速率；过低时形成求解任务。
3. 在硬件仿真程序 CFG 上把已到达点作为 source，附近未到达点作为 destination；用 hook 关联原输入指令序列。
4. 具体执行前缀，保存 source 的内部状态；angr/VEX/Z3 从该状态探索到 destination。
5. 将原前缀和新后缀拼接，放回共享 corpus，恢复快速变异。实际仿真核实是否获得覆盖。

主要覆盖的是稀有条件阻挡的硬件控制流区域。论文还评价 toggle coverage；不能把所有决策都假定成相同的逐位 toggle 新颖性算法。四个 RISC-V SoC 基准的图10/11报告十小时内分支接近100%、toggle最高约90%；分母、设计和时间限定不能迁移到另一CPU，更不能由此声称 bug-free。其“总能更快”理论表述也依赖论文假设，本讨论不外推。

与从 reset 开始的形式求解相比，关键是复用具体前缀缩短求解范围。它分析的是实现仿真模型，而非 ISA 参考模型。

### SysFuSS：将同类机制用于系统级固件

[全文](https://arxiv.org/html/2602.02243v1)，重点 §III、IV-A。

使用 LibAFL＋QEMU 采集 AFL 风格基本块边，记录中间 PC／寄存器／内存。平台期从已覆盖区域边界选 source/destination，优先较浅任务并限制队列；按论文描述用动态污染关系选择符号输入字节，angr/Z3 求局部路径，生成物重新入库。

作者报告六个基准的分支覆盖改善；但这是固件执行层的结论，不是硬件内部覆盖结论。中间状态初始化、输入与前缀串接以及环境一致性是可实现性要点；论文描述不代替本项目接口已具备的证明。

### S²F：反馈决定“在哪条路径上下文求解、在哪里多采样”

[全文](https://arxiv.org/html/2601.10068v1)，重点 §III、IV-C–F。

架构为 AFL＋coordinator＋SymCC；同一程序构建 fuzzing、符号执行、路径采集三个版本。coordinator 维护轻量执行树和 ICFG，同一静态分支在不同路径前缀下可以保留为不同探索任务，避免全局位图过早剪枝。

主决策使用两个估计：历史分支命中频率近似 fuzzing 难度，分支之后静态可达的未覆盖代码行数近似 future reward。后者不检查所有路径可行性，是启发式估计。

容易随机命中的部分留给 fuzzer；困难且有收益的部分求解；困难且通向较大未探索区域的部分进行多解采样。采样使用路径条件的多面体或区间近似，再经具体执行进入后续探索。它不是假设“输入值均匀采样＝行为均匀覆盖”。

作者在15个程序、每工具六次24小时实验中报告：边覆盖比 SymCC 平均高6.14%；栈顶三帧去重的 crash 数57对AFL++的43，增加32.6%。两个百分数的比较基线不同；crash去重也不等于独立根因。消融还显示保留更多任务但不改调度并非普遍有益，所有分支都采样也不是其最佳方案。

### ColorGo：将定向搜索放进编译后的 concolic 程序

[全文](https://arxiv.org/html/2505.21130v1)，重点 §3.1–3.3、4.3、5。

编译时从目标向前标记可达子图，运行时在执行将离开目标方向的分支求解，生成纠偏输入。当前路径前缀下不可满足的目标方向可被剪除；不能推断任意上下文的全局不可达。新输入入栈优先执行，形成快速深度搜索。

它并非“普通 AFL 外接一个停滞后唤醒的 solver”。主要反馈是目标可达范围及约束可行性，主要效果指标是到达目标和重现指定错误所需时间。作者报告相对 AFLGo 最高100倍；不能将定向目标收益解释成全局覆盖更优。

### 技术前史：HyPFuzz（USENIX Security 2023）

[正式论文](https://www.usenix.org/system/files/usenixsecurity23-chen-chen.pdf)，重点 §4.2–4.5。单列年份，不计作2025–2026新工作。

未覆盖点 → 自动生成 SVA cover property → JasperGold 找实现执行轨迹 → 转成可供 fuzzer 使用的指令测试 → 邻域变异 → 更新覆盖。按近期单位时间新增覆盖速率在 fuzzer 和形式工具间切换；模块深度、剩余覆盖点和驱动关系影响目标选择。

它是硬件形式可达性辅助测试，不能简单等同于沿软件路径翻转条件的 concolic execution。它解释 FuSS 为什么进一步强调“从已到达中间状态继续，而非总从初态重新找整条轨迹”。

## 7. 起承转合：反馈是在何处遇到瓶颈后改变的

1. **先解决可观测性与吞吐**：用低成本结构覆盖替代盲测；无法插桩时选可稳定采集的外部模式（SPFuzz）。
2. **结构覆盖过早饱和或混淆数据状态**：增加数据流关系、路径上下文、语义摘要（FuzzRDUCC、S²F、GraphFuzz）。
3. **细化后产生重复或开销**：选择性插桩、位置无关抽象、分桶、控制历史长度；细度与成本一起设计。
4. **反馈指明目标，但变异到不了**：引入实现层或软件层的选择性求解（FuSS、SysFuSS、ColorGo）。
5. **同一指标在不同区域和阶段价值不同**：模块加权、稀有点加权、阶段化选样（HiFuzz、ReFuzz、GoldenFuzz）。
6. **覆盖增加仍未转化为更多错误**：在共同 bug 集上检验整条反馈链（Encarsia），并把对照与消融独立于所优化的覆盖。

这几条路线同时存在。不能从论文数量或某条曲线推断一种指标全面支配另一种。

## 8. 读论文时保留的判断问题

- 同一代码边、不同输入为什么可能重要？该反馈是否区分它们？
- 原始特征是什么，抽象时舍弃了什么？若记录全部原值，成本和噪声是多少？
- 新点／稀有点／接近目标分别怎样影响留种、变异次数和求解任务？
- 求解器运行在哪一层模型，反馈来自哪一层执行？两者如何建立对应？
- 观测覆盖、用于调度的反馈、模型判错是否被混淆？
- 论文效果由覆盖定义、调度、种子、生成器还是成本变化造成？是否有适当消融？
- 结果是新特征、新crash还是独立bug？报告的基线、预算和统计是否一致？

本文暂不为本项目选择具体覆盖。先理解“什么行为应当被区别、什么差异可以合并、付出多少观测和求解成本”，再进入采样反馈指标的讨论。
